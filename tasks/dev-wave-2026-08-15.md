## 2. Invariants that were FALSE before this wave

Each of these was something the code's own comments asserted. All were falsified
against current source, not against historical prose.

| Claimed invariant | Reality |
|---|---|
| `update_config`'s allowlist is anchored to compiled-in defaults, so a hostile push cannot widen it | `this.config` **aliased** `DEFAULT_CONFIG` and `loadConfig` mutates it — one poisoned origin widened the allowlist for every later push |
| Confirmed revocation destroys all tenant-bound device state | One rejecting `SecureStorage.remove` skipped every later removal **and** the re-pair; the device froze on the revoked tenant's frame and resumed it after reboot |
| Cache is purged on revocation and never resurrected | No clear-generation guard on the Android manager; an in-flight download rewrote the purged cache |
| `setExpectedTenant` binds the cache to the current tenant | `init()`'s early return made it a no-op after first use |
| Only a 410 destroys credentials; transient errors never de-pair | The native `get()` deleted the entry on **any** exception, so the JS retry budget was decorative |
| The screen is never black and always recovers | An un-sandboxed `webpage` iframe could navigate the app away permanently |
| Tenant suspension fails closed | Cleared on **any** reconnect — and the deployed gateway has no suspension check at all |
| The app document's origin is one no remote URL can match | `androidScheme: 'https'` with no `hostname` makes it exactly `https://localhost` |

## 3. The finding with the widest blast radius

**`deliveryAck` was live in production and completely inert.** The realtime
server's whole delivery-guarantee layer — 10s ack timeout, Redis requeue,
heartbeat replay with backoff — was deployed and never triggered, because no TV
client advertised the capability. Finding none, the server took the legacy path:
emit into the socket and return `delivered: true`.

Consequence, verified against the production deploy `d323434e`: a **command**
emitted into a half-open socket (TCP dead, server hasn't noticed, up to ~45s) was
**permanently lost, silently**, while the dashboard reported it delivered and
wrote an audit row. Commands are not re-derivable from DB state the way content
is. That is the single sharpest reason the capability exists.

The ack semantics are forced by what the server actually does, not by taste — the
server has **no attempt counter, no dead-letter and no give-up** for a nacked
payload, and its circuit breaker is bypassed by the connect-time replay path. So
the client never nacks. Full derivation is in the PR #38 description.

## 4. What review changed

Independent reviewers, each of which had not seen the implementer's report,
materially changed the outcome three times:

1. **The first crash ladder was terminal.** Review traced every relaunch path and
   proved a terminal hold meant a **dark screen until a human power-cycles the
   TV**, reachable from transient causes such as an asset that OOMs the main
   thread — strictly worse than the unbounded 3s loop it replaced. The ladder is
   now capped, never terminal.
2. **The first cache fix did not deliver its invariant**, and one change turned a
   failed purge from fail-closed to **fail-open**. Proven with runtime probes and
   reproduced as red tests before being fixed.
3. **A mutation audit found the headline native fix completely unguarded** —
   deleting the call that restores the screen after renderer loss left all 65
   Java tests green, because the wiring tests called the recorded method directly
   and never went through `MainActivity`. The same defect class those tests were
   added to fix, one call frame up.

## 5. Verification posture

- Web tests **314 → 530+**; Android JVM tests **5 → 100**.
- Every production change is mutation-proven: the line is reverted and the test
  must go red. Several mutations survived on the first pass and the **tests were
  strengthened rather than the result accepted**.
- The `deliveryAck` contract is bound across a **real process boundary** — an
  in-process Socket.IO server, the real client, and the gateway's own predicates
  transcribed verbatim with `file:line` citations. Measured justification:
  changing the transcribed predicate turns 9 of 11 boundary tests red while every
  mock test still passes.
- The suite was failing **~1 run in 6** under parallel load. A gate that noisy
  cannot distinguish the next real regression from noise; it was fixed at the
  harness level (real event-loop yields, bounds on real elapsed time, and a
  helper that throws instead of returning silently) rather than by re-running.

### What the boundary test still cannot catch
Stated because it matters more than what it can: it runs a **transcription**, not
the gateway, so a divergence that updates neither is certified wrong with full
confidence. There is no auth path, no Redis, none of the four real
`emitWithDeliveryAck` call sites, and a loopback socket in one process can never
go half-open — which is the exact failure the capability exists to fix. The
cheapest durable fix is a truth-table test in the Vizora repo so a server-side
change reddens *its* CI.

## 6. Deferred, with reasons — do not lose these

1. **Un-assigning a playlist never clears the screen.** There is no client "stop
   showing this" primitive. After a dashboard unassignment the panel keeps
   displaying the removed playlist indefinitely. The backend calls this "by
   design"; it is a product decision to re-take, not a patch, and it sits against
   the never-black invariant.
2. **`?token=` on same-origin media URLs** for `<img>`/`<video>`, which cannot
   send headers. Frame navigations no longer carry it. Durable fix is
   short-lived per-asset tokens — a backend change.
3. **No max-staleness bound on cached content.** Neither side has a TTL concept.
4. **Offline impressions are dropped** — emission is gated on socket connectivity
   with no queue, so proof-of-play is unbacked exactly when the cached loop runs.
5. **Backend: the ack is a phantom for non-local sockets.** `fetchSockets()`
   returns a `RemoteSocket` when realtime is scaled past one instance, and its
   ack callback fires ~1ms with a timeout error that `getAckError` reads as
   success. Only `instances: 1` (`ecosystem.config.js:63`) prevents it today.
   **File before realtime is ever scaled horizontally.**
6. **Backend: `reboot`/`update`/`screenshot` are acked as delivered.** The client
   cannot implement them and must not nack. The operator therefore gets a
   "delivered" receipt for an action that will never occur. Correct fix is a
   `not_supported` outcome distinct from `delivered`, server-side.
7. **Renderer/JS wedge is undetectable** — process alive, WebView frozen,
   heartbeat still emitted from the same context. A frozen device reports healthy.
8. **LMK / ANR / native SIGSEGV / force-stop produce no relaunch.**
9. **F39 terminal holding never self-heals** — a keystore unavailable at boot
   strands the screen on "contact support" permanently, from a cause the code
   itself calls transient.
10. **Cache orphan leak** — files written before a failed rmdir become invisible
    to the LRU and are never evicted.

## 7. Release status — 1.3.16 is PREPARED, NOT PUBLISHED

Version bumped in all five sites (`package.json`, `versionCode` 10146,
`versionName`, `tizen/config.xml`, `webos/appinfo.json`). The Tizen and webOS
manifests had **drifted 14 releases behind** at 1.0.1; they are now stamped from
`package.json` at package time and guarded by a CI check, so the drift cannot
recur.

### This wave did NOT build or publish an APK. Two reasons, both structural:

**a. Publication requires a NEW operator Gate A approval bound to bytes that do
not exist yet.**

Stated precisely, because an earlier draft of this file got it wrong. Gate A in
`deploy/tv/release.json` is **not null** — it is filled in and machine-bound:
`artifactApprovedSha256 = 95D1BC01…C74E2383`, `artifactApprovedBy = Srini`,
`artifactApprovedAt = 2026-08-13`. Gate B (signing-key durability) is likewise
closed. Both were satisfied **for 1.3.15**, and the scope note says so in terms:
*"APPROVED 2026-08-13 for 1.3.15, bound to apkSha256 95D1BC01… and nothing
else."*

So the blocker is not an empty field. It is that the approval is bound to one
exact artifact hash and a rebuild voids it — a property the file now enforces
mechanically rather than only in prose. A 1.3.16 APK has a different SHA-256,
therefore it needs a **fresh operator artifact approval bound to the new bytes**,
which cannot exist until those bytes exist. Copying, editing or re-pointing the
existing binding would be forging a human control, which the file explicitly
forbids.

**b. The signing material is not reachable from a clean worktree.**
`keystore.properties` and `vizora-release.jks` are gitignored and exist only in
the primary checkout. `rootProject.file("keystore.properties")` resolves per
worktree, and `build.gradle` applies the release signing config **only if that
file exists** — so a release build from a worktree silently produces an
**unsigned** APK. That is a fail-open on the signing path and is worth closing
independently of this release.

### Before 1.3.16 can ship

**Two of these are now HARD GATES, not decisions.** Operator directive, 2026-08-16:

- **G1 — Sentry must be configured.** 1.3.16 ships with telemetry live. This wave
  added `reportEvent` specifically for command replay/dedupe failures, purge
  failures, heartbeat-ack errors and recovery conditions; shipping those paths
  dark removes a large part of the operational safety case. The DSN is **not** to
  be hardcoded or committed, and no secret-bearing `.env` goes in the repo. The
  gate is mechanical: **`__VIZORA_SENTRY_CONFIGURED__` must read `true` out of the
  BUILT ARTIFACT** before Gate A is sought. If no DSN has been supplied at that
  point, the correct terminal state is `WAITING_FOR_SENTRY_DSN` — an external
  configuration dependency, **not** permission to build a blind release.
- **G2 — release signing must fail closed.** `build.gradle` had two fail-open
  guards (`signingConfigs.release` populated only if `keystore.properties` exists;
  the release build type dropping `signingConfig` entirely otherwise), and
  `rootProject.file(...)` resolves **per worktree** — so a release build from any
  clean worktree silently produced *unsigned* bytes, with the unconditional
  output rename erasing the `-unsigned` filename tell. A release build must now
  refuse rather than emit unsigned, while `testDebugUnitTest` continues to run
  with no keystore (CI depends on that).

## 8. Open operator decision: crash reporting may be entirely disabled

`VITE_SENTRY_DSN` is env-driven with a silent empty default, and **no DSN is
configured anywhere in this repo**. A release built today ships with JS crash
reporting fully off — which would void every safety argument in this wave that
rests on telemetry (`command_dedupe_*`, `device_purge_incomplete`,
`crash_loop_capped`, `heartbeat_ack_error`, …), silently.

The build was deliberately **not** made to fail closed, because that would block
a release on a credential this session cannot supply. Instead the artifact now
**self-describes**: `__VIZORA_SENTRY_CONFIGURED__` is stamped into the bundle so
the publish-side verifier can assert telemetry is live in the exact bytes about
to be uploaded. Set a DSN, or accept 1.3.16 as a blind build knowingly.
